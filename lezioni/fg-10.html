Interfacce, zone e VLAN

Modulo Fortinet Lezione 10 28 min di lettura

Alla fine di questa lezione saprai

  • Riconoscere tutti i tipi di interfaccia di FortiOS e sapere a cosa servono
  • Configurare una sottointerfaccia VLAN e capire cosa comporta
  • Governare quali servizi di amministrazione sono raggiungibili su ogni interfaccia
  • Usare le zone conoscendone il rischio

Su FortiOS tutto è un'interfaccia. Porte fisiche, VLAN, aggregazioni, tunnel VPN, l'accesso remoto degli utenti: per il firewall sono tutti oggetti dello stesso tipo. È il punto che, una volta capito, rende ovvie le policy — perché una regola non è altro che «da questa interfaccia a quest'altra».

Il tunnel è un'interfaccia: è questo che sblocca la comprensione

Finché pensi al tunnel come a «una VPN», le regole restano misteriose. Nel momento in cui lo pensi come una porta in più sull'apparato, tutto si ordina: puoi metterlo in una regola, dargli una rotta, inserirlo in una zona, esattamente come faresti con una porta Ethernet.

E la domanda «perché il traffico non passa nel tunnel?» diventa la stessa domanda che faresti per qualsiasi altra porta: esiste una regola per quella coppia?

Il ruolo, e perché la finestra grafica cambia

A ogni interfaccia si assegna un ruolo — interna, esterna, zona demilitarizzata, non definito. Non cambia il comportamento del traffico: cambia quali campi ti mostra la finestra grafica.

È una comodità che confonde chi non lo sa: un'interfaccia marcata come interna non mostra le opzioni tipiche di una connessione verso l'operatore, e sembra che l'apparato «non le supporti». Se cerchi un campo e non c'è, controlla il ruolo prima di concludere altro.

La riga più importante di ogni interfaccia

allowaccess decide chi può parlare con il firewall

Su ogni interfaccia si dichiara quali servizi di amministrazione rispondono lì sopra: la finestra grafica, l'accesso a riga di comando, il ping, i protocolli di monitoraggio.

config system interface
    edit "internal"
        set allowaccess ping https ssh
    next
end

── e sull'interfaccia verso l'operatore: ───────────
   il meno possibile. Idealmente niente, o solo ping

Lasciare l'amministrazione raggiungibile dall'interfaccia esterna è uno dei rilievi più gravi che puoi trovare su un apparato. Significa che la pagina di accesso del firewall è esposta a Internet, e ogni vulnerabilità nota di quella versione diventa immediatamente sfruttabile. Su ogni apparato che prendi in carico, questa è una delle prime righe da guardare.

Le sottointerfacce VLAN

Si crea una sottointerfaccia sopra una porta fisica, indicando il numero della VLAN. Da quel momento è un'interfaccia come le altre: ha un indirizzo, può distribuire indirizzi, compare nelle regole.

Una VLAN dal principio
config system interface
    edit "vlan20-ospiti"
        set vdom "root"
        set interface "internal"      # la porta fisica sottostante
        set vlanid 20
        set mode static
        set ip 10.10.20.1 255.255.255.0
        set allowaccess ping          # sugli ospiti, niente amministrazione
        set role lan
        set description "rete ospiti — ticket 1234"
    next
end
Perché creare la VLAN non basta

Creata la sottointerfaccia, il firewall sa gestire quella VLAN. Ma lo switch a valle deve mandargliela etichettata, sul collegamento fra i due — il trunk.

Se il firewall ha la VLAN 20 e lo switch non la manda etichettata su quel cavo, non arriva niente e sembra un problema del firewall. È il punto in cui i due mondi si toccano, ed è esattamente quello che costruirai a mano nel modulo Switching, lezione 7.

Le zone: comode, e con una trappola

Una zona raggruppa più interfacce per scrivere una regola sola. Con sei tunnel verso sei filiali, una regola su una zona sostituisce sei regole identiche.

Il settimo tunnel che nessuno ha messo nella zona

La trappola è quella della lezione 8, e vale la pena ripeterla perché è silenziosissima: una regola costruita su una zona copre solo ciò che è dentro quella zona. Un tunnel aggiunto due anni dopo, da un'altra persona, per un altro progetto, non ci è mai entrato.

A colpo d'occhio la configurazione sembra già pronta. Non lo è, e non c'è nessun messaggio che te lo dica.

Due accorgimenti: quando crei un tunnel nuovo, chiediti subito se va in una zona esistente; e quando diagnostichi, apri la zona e leggi i membri invece di fidarti del nome.

Un'interfaccia dentro una zona non si usa più da sola

Una volta che un'interfaccia entra in una zona, le regole si scrivono sulla zona, non più sulla singola interfaccia. Se avevi regole che la citavano direttamente, vanno riviste.

Per questo le zone si progettano all'inizio: aggiungerle a configurazione avviata comporta di ritoccare tutto ciò che già esisteva, ed è il genere di lavoro in cui si rompe qualcosa.

Prima: guarda cosa c'è
show system interface
get system interface physical
show system zone

── e la riga che conta di piu, per ogni interfaccia ─
show full-configuration system interface | grep -A2 allowaccess
Poi: due VLAN e una zona
config system interface
    edit "vlan10-uffici"
        set interface "internal"
        set vlanid 10
        set ip 10.10.10.1 255.255.255.0
        set allowaccess ping https ssh
        set role lan
    next
    edit "vlan20-ospiti"
        set interface "internal"
        set vlanid 20
        set ip 10.10.20.1 255.255.255.0
        set allowaccess ping
        set role lan
    next
end

── raggruppale, e osserva cosa cambia ──────────────
config system zone
    edit "reti-interne"
        set interface "vlan10-uffici" "vlan20-ospiti"
    next
end

Ora la verifica che insegna qualcosa. Prova a creare una regola che usi vlan10-uffici come interfaccia di partenza.

Non te lo lascerà fare: quell'interfaccia adesso appartiene a una zona, e le regole si scrivono sulla zona. È la conseguenza pratica del riquadro qui sopra — molto più chiara vista che letta. Poi rimuovi la zona e nota che le interfacce tornano utilizzabili da sole.
