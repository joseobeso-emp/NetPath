Le policy: coppia di interfacce e deny implicito

Modulo Fortinet Lezione 12 32 min di lettura

Alla fine di questa lezione saprai

  • Scrivere una regola completa e sapere cosa fa ogni campo
  • Capire l'ordine di valutazione e riconoscere una regola oscurata
  • Sapere cosa succede al traffico che non corrisponde a nessuna regola
  • Costruire regole che fra due anni si possano ancora capire e manutenere

La policy è il cuore di FortiOS: tutto ciò che hai costruito finora — interfacce, oggetti, servizi — esiste per finire dentro una regola. Qui vediamo com'è fatta, in che ordine viene valutata, e le due cose che rendono il comportamento sorprendente per chi arriva da altri mondi.

Anatomia di una regola

Tutti i campi che contano, in una regola sola
config firewall policy
    edit 0                                # 0 = creane una nuova
        set name "uffici -> gestionale"
        set srcintf "vlan10-uffici"          # ── da dove ENTRA
        set dstintf "vlan30-server"          # ── da dove ESCE
        set srcaddr "rete-uffici"
        set dstaddr "srv-gestionale"
        set service "gestionale-web"
        set schedule "always"
        set action accept
        set logtraffic all                  # ── NON e automatico
        set comments "accesso al gestionale — ticket 1234"
    next
end
CampoCosa decideSe sbagliato
srcintf · dstintfIl percorso autorizzato La regola non corrisponde mai. È l'errore numero uno
srcaddr · dstaddrChi, verso cosaNessuna corrispondenza
serviceQuali porteAlcune funzioni vanno, altre no (anello 4)
scheduleQuandoFunziona a certe ore e non ad altre
actionPermetti o rifiuta—
natSe tradurre la sorgenteIl traffico parte con un indirizzo che la destinazione non accetta
logtrafficSe registrareNessuna traccia: diagnosi impossibile a posteriori

Il principio che genera più ticket di tutti

Una regola autorizza una tratta, non una destinazione

Lo hai già incontrato nella lezione 8, e qui lo mettiamo in pratica. rete-interna → server e vpn-utenti → server sono due regole diverse, anche se la destinazione, gli indirizzi e il servizio sono identici.

Ogni volta che qualcuno ti dice «ma la regola c'è», la domanda da fare è una sola: «c'è per quella coppia di interfacce?» Nove volte su dieci la risposta è no, e il ticket si chiude in due minuti.

L'ordine, e le regole che nessuno raggiunge

Come si scopre un oscuramento, senza leggere cento regole 
── quale regola deciderebbe questo flusso? ─────────
diagnose firewall iprope lookup 10.10.10.25 54000 \
    10.10.30.50 3389 6 vlan10-uffici

   se restituisce 2 invece di 3, hai trovato
   l'oscuramento senza generare un solo pacchetto

── e le regole mai usate, tutte insieme ────────────
diagnose firewall iprope show 100004 <id>
   hit count a zero = o e inutile, o e oscurata,
   o quel traffico non passa da qui

La regola si sposta, non si riscrive: nella finestra grafica si trascina, da riga di comando si usa il comando di spostamento indicando prima o dopo quale identificativo.

Il rifiuto implicito

In fondo c'è sempre una regola che non vedi

Ciò che non è espressamente permesso è negato. Quella decisione non compare nell'elenco, ma nei log ha una firma inconfondibile: identificativo della regola uguale a zero.

Quando vedi policyid=0 con azione di rifiuto, non stai cercando una regola sbagliata: stai cercando una regola che non esiste. È una distinzione che cambia completamente dove guardi — e nove volte su dieci il motivo è la coppia di interfacce.

La registrazione non è automatica

Una regola senza registrazione è traffico invisibile

Se logtraffic non è impostato su tutte le sessioni, quel traffico passa senza lasciare alcuna traccia. Il giorno in cui qualcuno chiederà cosa è successo martedì scorso su quella rete, la risposta sarà: non lo sappiamo.

È un rilievo che troverai spesso — intere serie di regole fra reti interne senza registrazione, quindi nessuna visibilità sul traffico fra le VLAN. Su ogni regola che scrivi tu, accendila. Sulle regole esistenti di un cliente, accenderla è una modifica a rischio zero e beneficio immediato: proponila.

La regola scritta bene

Sei criteri, e valgono su qualsiasi firewall
  1. La più stretta possibile: sorgente precisa, destinazione precisa, solo le porte che servono. «Tutto» si scrive in un secondo e si paga per anni.
  2. Un nome che dice a cosa serve, non cosa fa tecnicamente.
  3. Un commento con il perché e il riferimento al ticket o alla data.
  4. Registrazione accesa. Sempre, e almeno durante le prove.
  5. Nella posizione giusta: le regole specifiche sopra quelle generali.
  6. Verificata con i contatori, non con «dovrebbe funzionare».

Alla tastiera

Crea un oscuramento di proposito, e poi trovalo

È l'esercizio che ti fa capire l'ordine meglio di qualsiasi spiegazione: prima lo costruisci, poi lo diagnostichi come faresti su un apparato altrui.

Costruisci
# 1. una regola larga
config firewall policy
    edit 0
        set name "uffici - tutto"
        set srcintf "vlan10-uffici"
        set dstintf "vlan20-ospiti"
        set srcaddr "all"
        set dstaddr "all"
        set service "ALL"
        set schedule "always"
        set action accept
        set logtraffic all
    next

# 2. e SOTTO, una regola che vorrebbe bloccare qualcosa
    edit 0
        set name "blocca desktop remoto"
        set srcintf "vlan10-uffici"
        set dstintf "vlan20-ospiti"
        set srcaddr "all"
        set dstaddr "all"
        set service "RDP"
        set schedule "always"
        set action deny
        set logtraffic all
    next
end
Diagnostica
# quale regola decide davvero per il desktop remoto?
diagnose firewall iprope lookup 10.10.10.25 54000 \
    10.10.20.50 3389 6 vlan10-uffici

# restituisce la regola LARGA, non quella di blocco.
# La regola di blocco esiste, sembra giusta,
# e non serve a niente.

# conferma con i contatori
diagnose firewall iprope show 100004 <id-della-regola-deny>
   hit count: 0

# ora spostala sopra e ripeti il lookup

Quando finisci, cancella entrambe le regole. Una regola che permette tutto fra due reti, lasciata lì dopo un esercizio, è esattamente il tipo di debito che nella lezione 4 imparavi a cercare sugli apparati altrui.
