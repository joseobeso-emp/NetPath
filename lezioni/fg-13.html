NAT: SNAT, DNAT e i VIP

Modulo Fortinet Lezione 13 30 min di lettura

Alla fine di questa lezione saprai

  • Distinguere traduzione della sorgente e della destinazione, e sapere quale serve quando
  • Costruire una pubblicazione corretta e verificarla
  • Riconoscere i tre errori che fanno fallire le pubblicazioni
  • Gestire il caso dei client interni che raggiungono il proprio server dall'indirizzo pubblico

Il NAT è il punto in cui più configurazioni «corrette a leggerle» non funzionano. Non perché sia difficile, ma perché richiede che tre oggetti diversi combacino — e se uno solo non combacia, non c'è nessun messaggio a dirtelo.

Spiegato a un dodicenne: il centralino dell'albergo

Un albergo ha un solo numero di telefono e duecento camere.

Quando un ospite chiama fuori, il destinatario vede il numero dell'albergo, non quello della camera: è la traduzione della sorgente. Il centralino annota chi ha chiamato, così quando arriva la risposta sa a quale camera girarla.

Quando invece qualcuno da fuori chiama l'albergo e chiede il ristorante, il centralino gira la chiamata alla camera 12, dove c'è il ristorante: è la traduzione della destinazione. E qui sta il punto che fa fallire le pubblicazioni: il centralino deve sapere che «ristorante» corrisponde alla 12, e il portiere all'ingresso deve avere l'ordine di lasciar passare quella richiesta. Due cose distinte, e servono entrambe.

Traduzione della sorgente: le due forme

Con l'indirizzo dell'interfaccia, o con un pool
── la forma semplice: esce con l'indirizzo ─────────
   dell'interfaccia di uscita
config firewall policy
    edit 10
        set nat enable
    next
end

── con un pool: quando la destinazione accetta ─────
   solo certi indirizzi (il caso della lezione 8)
config firewall ippool
    edit "pool-verso-fornitore"
        set type overload
        set startip 10.200.78.10
        set endip 10.200.78.10
    next
end

   e poi, IN DUE PASSAGGI (lezione 8):
   prima  set nat enable
   poi    set ippool enable + set poolname

Pubblicare: l'oggetto VIP

Due modi, con conseguenze diverse
══ A · TRADUZIONE COMPLETA, senza porte ════════════
config firewall vip
    edit "pub-server-web"
        set extip 203.0.113.10
        set mappedip 10.10.30.50
        set extintf "wan1"
    next
end
   TUTTE le porte passano: e la POLICY a decidere
   quali. Piu semplice, ma la policy deve essere
   stretta sul servizio

══ B · CON TRADUZIONE DI PORTA ═════════════════════
config firewall vip
    edit "pub-server-web-443"
        set extip 203.0.113.10
        set mappedip 10.10.30.50
        set extintf "wan1"
        set portforward enable
        set protocol tcp
        set extport 443
        set mappedport 443
    next
end
   ⚠ da qui in poi la porta del VIP e quelle
   dell'oggetto servizio DEVONO combaciare
I tre errori che fanno fallire le pubblicazioni

1 · Porta del VIP e oggetto servizio che non combaciano. Il VIP traduce la 5061, la policy usa un servizio che contiene solo la 443: la regola non corrisponderà mai. E leggendo i due oggetti separatamente sembrano entrambi corretti.

2 · Due VIP sullo stesso indirizzo pubblico con porte sovrapposte. Vince la policy più in alto, e la nuova non viene mai raggiunta. Sintomo: «la pubblicazione vecchia funziona, quella nuova no».

3 · Il VIP creato ma non usato da nessuna policy. Un VIP è un oggetto: da solo non pubblica niente. Va messo come destinazione di una regola che arriva dall'esterno.

Il caso del giro su sé stessi

«Da fuori funziona, dall'ufficio no»

Hai pubblicato un server. Da casa si raggiunge benissimo. Dall'ufficio, usando lo stesso nome pubblico, no.

Il motivo: il client interno manda la richiesta all'indirizzo pubblico, il firewall la traduce e la gira al server — ma il server vede arrivare una richiesta da un indirizzo della sua stessa rete e risponde direttamente, senza ripassare dal firewall. La risposta arriva al client da un indirizzo diverso da quello a cui aveva scritto, e viene scartata.

Le due soluzioni, in ordine di preferenza: far risolvere il nome con l'indirizzo interno per chi sta dentro — è la soluzione pulita, si chiama risoluzione differenziata e l'hai vista nella lezione 1-20; oppure tradurre anche la sorgente sulla regola interna, così il server risponde al firewall invece che al client. La seconda funziona ma nasconde l'indirizzo vero del client nei log del server.

Verificare che il NAT stia facendo il suo lavoro

La tabella delle sessioni, filtrata
── ⚠ SEMPRE prima: i filtri restano impostati ──────
diagnose sys session filter clear

diagnose sys session filter dst 203.0.113.10
diagnose sys session filter dport 443
diagnose sys session list

── cosa cercare nell'output ────────────────────────
   policy_id=<quella che ti aspetti>
   hook=dnat act=dnat   → la traduzione in ingresso
                          sta avvenendo
   hook=snat act=snat   → quella in uscita

── su apparato diviso in partizioni, obbligatorio: ─
diagnose sys session filter vd <numero>
Il filtro delle sessioni resta impostato, e inganna

È la stessa trappola dei log. Il filtro che hai messo mezz'ora fa è ancora attivo, e i risultati che stai leggendo sono ristretti da una condizione che non ricordi.

Il modo in cui inganna è particolarmente insidioso: tutto sembra coerente. Vedi poche sessioni e concludi che il traffico non passa, quando semplicemente stai guardando attraverso una fessura. Azzera sempre prima di ogni nuova prova.

Alla tastiera

Pubblica un servizio, e rompi la pubblicazione di proposito

Fai girare un servizio sul Mac — basta un server web improvvisato — e pubblicalo attraverso il firewall.

Sul Mac: un server in una riga
cd /tmp && python3 -m http.server 8080
# resta in ascolto sulla porta 8080
Sul firewall: VIP, servizio, policy
config firewall vip
    edit "pub-prova"
        set extip <indirizzo-della-wan-del-60D>
        set mappedip <indirizzo-del-Mac>
        set extintf "wan1"
        set portforward enable
        set protocol tcp
        set extport 8080
        set mappedport 8080
    next
end

config firewall service custom
    edit "prova-8080"
        set tcp-portrange 8080
    next
end

config firewall policy
    edit 0
        set name "pubblicazione di prova"
        set srcintf "wan1"
        set dstintf "internal"
        set srcaddr "all"
        set dstaddr "pub-prova"     # ← il VIP come DESTINAZIONE
        set service "prova-8080"
        set schedule "always"
        set action accept
        set logtraffic all
    next
end

Verifica che funzioni, poi rompila in tre modi diversi e osserva ogni volta cosa cambia nei log e nelle sessioni:

  1. Cambia la porta dell'oggetto servizio da 8080 a 443, lasciando il VIP com'è. Guarda i log: cosa succede? Quale identificativo di regola compare?
  2. Rimetti a posto, e togli il VIP dalla destinazione della policy mettendoci all. Funziona ancora? Perché?
  3. Rimetti a posto, e crea un secondo VIP sullo stesso indirizzo pubblico e la stessa porta, con una policy più in alto. Quale delle due vince?

Cancella tutto alla fine. Ognuno dei tre casi che hai appena provocato lo incontrerai davvero, con la differenza che l'avrà creato qualcun altro e tu dovrai capirlo dai soli sintomi.
