IPsec site-to-site: fase 1, fase 2, selettori

Modulo Fortinet Lezione 19 34 min di lettura

Alla fine di questa lezione saprai

  • Capire cosa negoziano le due fasi e in che ordine
  • Sapere quali parametri devono essere identici sui due capi e quali no
  • Costruire un tunnel completo, con rotte e policy
  • Riconoscere gli algoritmi obsoleti e sapere quando vanno cambiati

Un tunnel IPsec si costruisce in due fasi, e capire cosa fa ciascuna è ciò che rende leggibili i messaggi di errore. La prima stabilisce un canale sicuro fra i due apparati; la seconda decide quale traffico può usarlo.

Le due fasi

Spiegato a un dodicenne: la riunione fra due aziende

Fase 1 — ci si presenta. I due delegati si mostrano il tesserino, verificano di essere chi dicono, e si mettono d'accordo sulla lingua in cui parleranno. Se uno parla solo italiano e l'altro solo tedesco, la riunione non comincia nemmeno.

Fase 2 — si decide l'ordine del giorno. Ora che si capiscono, stabiliscono di cosa possono parlare: questi tre argomenti sì, tutto il resto no.

Da qui i due errori tipici. «Non si capiscono» → problema di fase 1: il tunnel non sale affatto. «Si capiscono ma quell'argomento non è all'ordine del giorno» → problema di fase 2: il tunnel è su, e il tuo traffico non passa. Due sintomi completamente diversi, e la prossima lezione li smonta entrambi.

Il tunnel, pezzo per pezzo

Fase 1
config vpn ipsec phase1-interface
    edit "tunnel-filiale"
        set interface "wan1"
        set ike-version 2
        set peertype any
        set remote-gw 198.51.100.20
        set psksecret "..."
        set proposal aes256-sha256
        set dhgrp 14
        set dpd on-idle          # ← vedi riquadro
        set comments "filiale nord — referente: Paolo"
    next
end
Fase 2 — i selettori
config vpn ipsec phase2-interface
    edit "tunnel-filiale-p2"
        set phase1name "tunnel-filiale"
        set proposal aes256-sha256
        set src-subnet 10.10.0.0 255.255.0.0    # la MIA rete
        set dst-subnet 10.20.0.0 255.255.0.0    # la SUA
        set auto-negotiate enable
    next
end
E i due pezzi che tutti dimenticano
── la rotta verso le reti remote ───────────────────
config router static
    edit 0
        set dst 10.20.0.0 255.255.0.0
        set device "tunnel-filiale"   # il tunnel È un'interfaccia
        set comment "reti filiale nord"
    next
end

── e le policy: DUE, una per direzione ─────────────
config firewall policy
    edit 0
        set name "sede -> filiale"
        set srcintf "vlan10-uffici"
        set dstintf "tunnel-filiale"
        set srcaddr "rete-sede"
        set dstaddr "rete-filiale"
        set service "ALL"
        set schedule "always"
        set action accept
        set logtraffic all
    next
    edit 0
        set name "filiale -> sede"
        set srcintf "tunnel-filiale"
        set dstintf "vlan10-uffici"
        set srcaddr "rete-filiale"
        set dstaddr "rete-sede"
        set service "ALL"
        set schedule "always"
        set action accept
        set logtraffic all
    next
end
Un tunnel richiede quattro cose, non due

Fase 1 e fase 2 fanno salire il tunnel e basta. Perché ci passi traffico servono anche:

  • La rotta verso le reti remote, con il tunnel come interfaccia di uscita
  • Le policy, e due: una per ciascuna direzione. Una sola fa funzionare il traffico in un verso e non nell'altro — e produce sintomi che sembrano casuali
Il rilevamento del peer morto, e perché va acceso

Con il rilevamento impostato «su richiesta», i due capi non si scambiano segnali di vita finché non c'è traffico. Se l'altro capo sparisce senza avvisare — si spegne, cambia indirizzo — il tuo apparato continua a considerare il tunnel attivo e a mandarci dentro il traffico, che sparisce.

Su un apparato in produzione si è trovato esattamente questo: contatori di rilevamento a zero in entrambe le direzioni, e nessun controllo di salute sulle rotte del tunnel. Un guasto silenzioso dell'altro capo non avrebbe ritirato la rotta, e il traffico sarebbe continuato a finire in un tunnel morto.

Gli algoritmi obsoleti

Il tunnel che funziona oggi e cadrà definitivamente un giorno

Su tunnel costruiti anni fa troverai algoritmi di cifratura e di integrità superati, e gruppi di scambio chiavi troppo deboli per gli standard attuali. Il tunnel funziona: le due parti si accordano su quello che entrambe supportano.

Il problema è il futuro: il giorno in cui la controparte aggiorna il proprio apparato e smette di offrire quegli algoritmi, il tunnel non sale più — e succede senza preavviso, spesso di notte, dopo una loro manutenzione di cui nessuno ti ha informato.

Cosa fare: annotarlo come rilievo di priorità media, e programmare l'aggiornamento concordato con la controparte. Non si cambia da un lato solo: si fissa una finestra, si aggiungono le proposte nuove accanto alle vecchie su entrambi i capi, si verifica che rinegozi sulle nuove, e solo dopo si tolgono le vecchie.

Alla tastiera

Un tunnel vero, fra il 60D e il MikroTik

Hai due apparati di marche diverse: è il laboratorio ideale, perché ti costringe a far coincidere i parametri invece di copiare la stessa schermata due volte — che è esattamente la situazione reale quando l'altro capo è di un fornitore.

Lo schema del laboratorio
   rete 10.10.0.0/16          rete 10.20.0.0/16
        │                            │
   [ FortiGate 60D ]══ tunnel ══[ MikroTik hAP ax2 ]
        │                            │
   le due "sedi" sono due segmenti del tuo laboratorio

Procedi così, e annota tutto:

  1. Scrivi su un foglio i parametri concordati prima di configurare: versione, algoritmi, gruppo, chiave, selettori. È quello che faresti con un fornitore, e ti obbliga a decidere invece di scoprire.
  2. Configura entrambi i capi secondo il foglio.
  3. Aggiungi rotte e policy — su entrambi, e in entrambe le direzioni.
  4. Verifica che salga e che passi traffico.
Le verifiche sui due apparati
═══ sul FortiGate ══════════════════════════════════
get vpn ipsec tunnel summary
diagnose vpn ike gateway list name "tunnel-filiale"
diagnose vpn tunnel list name "tunnel-filiale"

/ip/ipsec/active-peers/print

/ip/ipsec/policy/print

Poi l'esercizio che insegna di più: cambia un solo parametro su un lato — il gruppo di scambio chiavi, o un algoritmo — e guarda cosa succede.

Vedrai il tunnel smettere di salire, e soprattutto vedrai quale messaggio compare. Quel messaggio è ciò che leggerai davvero quando un fornitore avrà configurato il suo capo in modo diverso dal tuo — ed è il tema della prossima lezione.
